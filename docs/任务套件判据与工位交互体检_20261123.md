# 任务套件判据与工位交互体检 · 2026-11-23

对应师兄那句"场景主要是要能实现交互，不是只要像就可以了，还要能确实的进行交互任务"，
以及基线口径（Spatial Forcing arXiv 2510.12276 / ROCKET arXiv 2602.17951：
LIBERO 四组各 10 题 + RoboTwin easy/hard）。

一句话结论：**四组 40 题在"初始态"这一侧全部判得出、且不白送（`unsolved` 40/40 well-formed）；
但在"做完态"这一侧暴露出两类真问题 —— ① 所有落点为"枪头散放在体积容器里"的判据物理上不成立
（96 支 tip 一放进 dish/孔板/台面就被求解器弹飞，z 落到 −19.5205 m），② 三台 ART 工位
（mini 离心机 / C1000 / 涡旋）此前根本不能交互：12 个部件 0 个碰撞体、drive 三项全 0、
限位被 MJCF→USD 二次换算放大到上万度。drive+限位那一半已经修到 `biolab_main_v08.usda`。**

适用范围：几何 / 关节级 / 单次短时 rollout（120–150 帧）。**不含**机械臂闭环，
所以这里验的是"场景能不能承载这套任务规格"，不是"策略能不能做成"。

## 二、判据坐标系的三条铁律（每一条都是量出来的，不是推的）

| 曾经过的假设 | 实测 | 后果 |
| --- | --- | --- |
| 刚体原点 = 包围盒中心，底面 = `pos_z − size_z/2` | 台面 `TableTopCollision_Physics` 顶面 **z=0.8717**，旧算法报 0.8592 | 差 12.5 mm，oracle 把物体埋进 10 mm 厚的台面板里 |
| 槽位锚点 = 槽底 | 三组锚点相对真实槽底偏移 **−49.6 / 0.0 / +13.5 mm** | "放稳"判据的 z 阈值对两组是错的 |
| PhysX 读到的位置是几何中心 | 是**刚体 prim 原点**（tip 用 dz=+0.000 通过验证） | 所有"底面贴住某高度"必须写成 `Z + (pos_z − bbox.min_z)` |

代码里对应 `task_defs.origin_lift()`：**用 `pos − bbox.min`，不用 `size_z/2`**，
后者默认原点在几何中心，对导入网格基本不成立，错了就是半个身位。

补充一条：体积容器的包围盒 min 是**外底**，不是内底，所以落点给 `外底 + 3 mm`；
深度互穿在 10 mm 厚的板里会被求解器**朝下**解算，然后一路穿出去 ——
物体掉到 −19.5 m 不是"场景里没有桌面"，是穿透（0.5·9.81·2² ≈ 19.6 m，正好对上）。
两种病因的修法完全相反，这就是为什么要盘静态碰撞体。

### 修法与分两批的理由

- **B 批（`--with-collision`，未落）**：给 12 个部件加 CollisionAPI + 按角色显式质量。
  默认不做，因为脚本自带的包围盒预检查报了实打实的互穿：

## 五、判据脚本这两个月欠的三笔账

1. **`rest` 拿错容器**：`Judge.rest[lid]` 存的是 `(pos, quat)` 一对，上一版整对当四元数
   传下去 → `ValueError: not enough values to unpack (expected 4, got 2)`。
   `got 2` 不是"四元数只有两个分量"，是拿错了容器。
2. **四元数排列不再靠猜**：`get_rigidbody_transformation` 的 rotation 实测是
   `carb.Float4(0,0,0,1)`，字段名齐全 → 按 `.w/.x/.y/.z` 取。
3. **reachable 必须真的驱动关节**：只搬物体的 oracle 对关节判据永远报假。
   关节驱动必须在 `tl.play()` 之后（与"物体必须 stop 时摆"时序相反），
   链式任务还要**按步依次驱动**并逐帧 latch —— "开盖…关盖"引用同一根轴，
   只看终态时两步互相否掉，中间那步在物理上从没发生过。

## 六、v07 上关节判据的假阳性（务必别当成功）

同一次 rollout 里 ThermalCycler 的 lid 在无弹簧（k=0）状态下**被重力摆到限位**，
读到 `ang = 108.86°`，而 `open_deg = −108.86` 的判据取的是 `|ang|`：
于是"开盖"这一步被**什么都不做**满足了。`lid_lever` 更离谱，读到 `162.72°`，
超出它 `−53.86…0` 的限位 —— 限位在这个构建里没生效（或 axis-angle 把两个部件的
复合旋转算到了一起）。

结论：A 批给了 stiffness 之后，"停在作者角度"才有物理保证，
关节判据才有意义。`unsolved` 模式里同一个盖子静止读数是 2.0°，
说明这是 rollout 过程中发生的，不是作者态 —— 这条只能靠 v08 的对照跑说清楚。

### 6C 世界轴：判据的符号从这一刻起才有意义

`physics:axis` 是**关节系**的轴，关节系 = body0 坐标系再套 `physics:localRot0`，
它跟世界的 X/Y/Z 不是一回事。换算落在 `scripts/survey_scene_assets.py:86`
（`Gf.Rotation` 在这套构建里没绑 `RotateVec`，四元数旋转就三行，自己算）。

本场景实测：**13 条 v07 关节里 12 条世界轴与字母不一致** ——
VortexGenie2 摆成 rotateXYZ=(0,0,90) 且 switch 的 localRot0 先把 X 转成 −X，
合成世界 **−Y**；ThermalCycler 盖/压杆 → −Y；离心盖 → +Y；移液器三条是**斜的**
[0.259, 0, 0.966]。A 类那 7 条恰好一致（localRot0 是单位四元数、工位 rotZ=0），
所以第一轮的驱动实测数字不受这条影响。

**别过度声称**：`|转角|` 与投影轴无关（任意相对旋转就是绕一根轴转一个角度，
拿垂直轴去投影只把符号打成 0），所以这条修正改的是**符号**，不是大小。
第六节那两个怪数（lid 108.86、lever 162.72）**不在它的解释范围内**，162.72 至今无解。
因此角度判据暂时仍按大小判，`axis` 缺失时报 `unmeasurable` 而不是猜 (1,0,0)
（`scripts/eval_task_goal.py:189`）；要收紧成带符号，得先把 v07 每条的期望符号实测重定。

### 6E 语义层补到 v09（#17 结掉）

为什么不往 `semantics_v07.usda` 里追加，而是另起一层：
链已经是 `v09 → v08 → semantics_v07 → v07`，老标签就是这么被引着的。若让
`semantics_v07` 再子层 `v09` 就是个**环**，而 USD 对环只静默裁一条弧、不报错 ——

默认输出名跟着 base_scene 的版本走（`semantics_v09.usda`），一层只服务一个场景版本。

实测：488 个 prim（manipulable 180 / receptacle 298 / articulated 14），
`check_semantics.py` 用 Isaac 自己 `get_labels` 的口径回读，**0 个孤儿**，
YAML 声明的 41 个类名全部落在现存 prim 上。
下游要"几何 + 标签"的完整场景，打开的是 `assets/scenes/semantics_v09.usda`，不是 v09。

### 6F 补货资产里的退化盒碰撞体（幽灵刚体）—— 孔板一直掉的真凶

症状：reachable 里 96 孔板**摆哪儿都掉到 z ≈ −2**，dz 恒等于 −3.0738；
同一批补货的皿和冻存管待在原地稳稳的。

根因在资产本体：MJCF→USD 出来的碰撞体写成 `def Box` + `custom normal3f[] extent`
+ `custom float size = 2`，既没有 UsdGeom.Box 真正读的 `extents`，`size` 也不是 schema 的
`double size`。USD 认这是个零尺寸盒，PhysX 建出来的形状半边长全 0 ——
等于这具刚体**没有任何有效碰撞体**，一进仿真就穿桌自由落体。
皿和管没事是因为它们各有一条写对的 `Cylinder`（radius/height + 真 extent）兜着，
而孔板 22 个碰撞体**全是 Box**，一个都不成立。

为什么场景里的原件偏偏没事：`WellPlate96` 那批在 v04 里是按 **prim 路径**逐条覆盖的
（改成 `Cube` + `size=2` + `xformOp:scale:physicalSize`）。覆盖写死在路径上，
v09 新加的副本 `WellPlate96_1` 走同一份资产但不是那条路径，拿回来就是没修的原始 Box。
**这就是"改资产"和"改场景里某条路径"的区别，也是补货这一步真正的坑。**

修法与校验：`scripts/fix_stock_colliders.py --write` 把三台资产的 39 个退化盒
（cryovial 1 / dish 16 / plate 22）全转成 v04 那套已验证写法，写完重新打开文件、
用 BBoxCache 逐条量半边长对 `physicalSize`，39/39 一致；重跑盘点后
`WellPlate96_1` 的碰撞体形是 0.120×0.080×0.0202 m（与原件一致）。
顺带否掉一个看着很像的假设：`_probe_penetration.py` 比视觉子树与碰撞子树的 min z，
孔板 Δ +0.0000、50 mL 管 −4.2 mm —— 不是"视觉网格埋进碰撞体"。

这套 USD 绑定踩到的 API 坑（都实测过，别再试第二遍）：

### 6Q 闭环评测 harness：replay/noop 已跑通（物体题）

`eval_task_goal.py` 新增 `--mode policy --policy replay|noop`（合并自 `_replay_probe.py` 原型，
原型已删）：

- **replay**：读一条 hdf5 的 `obs/agent_pos`，按列名映射回 prim，逐帧把被看刚体设成
  运动学并写位姿，跑完关掉 kinematic 让物理安定，再用现有判据判 success/fail。
- **noop**：什么都不做，同样判据，作为 0% 基线。
- 实测（seed0，`--settle 30`）：
  - `spatial_02`：replay **success**，noop **fail**（dxy 0.2 m）——区分度成立；
  - `long_horizon_02`：replay **fail**（第一步盖子角度 −0.01° vs −98.72°），
    原因是只回放了连杆位姿、没有回放关节 drive 目标，盖子被驱动拉回；noop 也 fail。
- 结论：**物体题的闭环评测已经能用**；关节链题要么在样本里补关节目标列，
  要么让 replay 把连杆位姿反解成 drive target。接 VLA 策略时把 replay 换成
  `policy(obs) → action` 即可，判据/成功统计不用动。
- 命令：
  `python -u scripts/eval_task_goal.py --mode policy --policy replay --gpu-cap --suite v01.4 --seed 0 --ids spatial_02 --settle 30`

3. 我们的场景是**新的下游域**（细胞培养），不是复现 LIBERO/RoboTwin；论文数字不能直接对标，

## 十、自动场景生成：SimFoundry 与替代路线（2026-11-27）

师兄建议"SimFoundry 也挺好的，可以看看；最近很多自动生成场景的方法"。核实结果如下。

### 10A SimFoundry 是什么（按官方 README / 论文）

- 全名 *SimFoundry: Modular and Automated Scene Generation for Policy Learning and Evaluation*，
  arXiv 2606.28276，NVIDIA GEAR + Stanford 等，**Apache-2.0**，仓库 `NVlabs/SimFoundry`。
- 输入：**一段桌面环绕视频**（无文字/图片入口）。输出：**OmniGibson 场景 + USD 资产 + 任务 YAML**；
  不是 Isaac Sim 原生工程，C 阶段要在 OmniGibson 里加载。
- 流水线 13 阶段：视频处理、深度、地面分割、物体分解、网格生成、位姿、物理编译、USD/OmniGibson 导出；
  另可生成 digital cousins、场景变体与任务提议。
- 硬门槛（README 原文）：**Linux + NVIDIA GPU + CUDA**、mamba/conda、ffmpeg、
  **约 250 GB 磁盘**、HF 账号、**Google Cloud/Vertex 或 Gemini API key**；
  需要申请 4 个门控 HF 模型（SAM3 / DINOv3 / RMBG-2.0，可选 FLUX）。
  24 GB 显存可跑，但 stage7 要加 `s7_mesh.low_vram=true`（默认约 29 GB）。
- 现状：V0 只做刚体 + 简单关节；**机器人数据生成/训练/评测标注 "Coming Soon"**；
  网格默认走 Hunyuan3D，产物受腾讯社区许可约束（不是 Apache）。

### 10B 本机能不能复现：不能（这一轮）

本机是 Windows + 已有 Isaac 6.x，且没有 Gemini/Vertex 账号与门控模型授权。
装 SimFoundry 需要独立 Linux 环境 + 250 GB + 云端 API，等于再搭一套栈；
而且它的输出是 OmniGibson 场景，回接到我们这套 Isaac 判据还要再做一层转换。
**结论：不在本机硬装；如果要做，放到一台 Linux 机器上按 10D 的 PoC 走。**

### 10C 其它自动生成方法（按输入模态）

| 输入 | 代表 | 输出 / sim-ready | 对我们的价值 |
| --- | --- | --- | --- |
| 单图 | PhysX-Anything (CVPR'26, 开源) | URDF/MJCF + 质量/质心/摩擦/关节限位 | 单件资产可用，整场景不行 |
| 视频 | SimFoundry；RoboScape（仅视频，不可仿真） | OmniGibson/USD | 单桌面 real2sim，见 10B |
| 文字 | Holodeck / SceneCraft / LayoutGPT | 场景布局/网格，**不带物理** | 只能当布局参考 |
| 文字→USD | Genie Sim Generator (AgiBot, 开源) | LLM 写 DSL → `scene.usda`，Isaac 原生 | 与我们现有资产/语义层最接近 |
| 程序化 | ProcTHOR / Infinigen / RoboCasa | 非 USD；RoboCasa 带关节 MJCF | RoboCasa 可参考任务/数据生成，不直接复用 |

### 10D 现实路线（按成本从低到高）

1. **布局级自动生成（最稳，1–3 周）**：现有仪器 USD + SimReady 耗材 + LLM/DSL 写布局，
   复用 388 个槽位锚点与语义层，自动产出 20 个台面布局变体并跑现有判据。
   验收：20/20 无碰撞、IK/放置可达、语义字段齐全、每布局能出 1 条 LIBERO 式样本。
   —— 这条和现在的 `task_defs --seed` 是同一层（任务/布局随机化），只是把"手写 YAML"换成"生成 DSL"。
2. **资产级 real2sim（2–4 周）**：对 5 件耗材拍单图 → TRELLIS.2/PhysX-Anything → USD + 凸包碰撞，
   在 Isaac 里做掉落 + 抓取验收（静置无穿透、抓取 ≥80%、单件 ≤30 min）。
3. **视频 real2sim（4–8 周）**：Linux + Gemini 环境跑 SimFoundry，只对**生物安全柜台面**做孪生，
   与手工 USD 对比。验收：物体召回 ≥80%、尺度误差 <2 cm、10 min 物理稳定、能采 1 条 pick-place；
   若人工修正 >3 min/件，判定不可替代手工。

### 10E 边界

- 我们的场景是**多工位、带关节仪器、长程任务**；SimFoundry 的强项是单桌面刚体，
  对离心机盖锁扣、移液器多级杆、孵育箱门这些关节/传动**基本要手写**（人工后处理 50–80%）。
- 透明件、小物体、单目尺度是 real2sim 的已知弱项；细胞培养耗材恰好透明件多。
- 因此"自动生成"在我们这里更现实的定位是：**布局/变体/耗材资产生成**，
  不是替代手工的仪器交互建模。
