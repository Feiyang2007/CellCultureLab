## 2. 实际使用的参数

`headless=False, create_new_stage=True, multi_gpu=False, sync_loads=False, limit_cpu_threads=4, width=960, height=540`，另加日志路径与 `--/rtx/hydra/mdlMaterialWarmup=false`。

顺序：先起空SimulationApp，再设置预热为false，再`context.open_stage()`。打开后，在会话层将`/Render`下原有的以下属性设false：

```
omni:rtx:scene:hydra:mdlMaterialWarmup
omni:rtx:material:db:syncLoads
omni:rtx:scene:hydra:materialSyncLoads
```

这是因为保存于场景的每视口设置可能覆盖全局值。没有使用`--no-threading`、没有专门关闭shaderdb的参数，也没有GUI隐藏参数。关闭预热/同步等待只改变加载方式，不取消最终材质编译，更不保证内存峰值一定降低。

## 建议的下一步

优先在用户自己的普通PowerShell里跑相同命令，保留脚本打印的真实缓存目录；先查任务管理器“性能→内存→已提交”的当前值与上限。关闭程序释放提交空间，并检查分页文件是否系统管理、有足够磁盘空间。不要只看物理内存剩余。

若再次发生bad allocation，记录当时提交内存，先处理容量/峰值问题。若提交空间充足而仍复现Slang栈顶崩溃，再进行原材质/中性材质与独立缓存目录的对照，最后考虑受控驱动对照。不要同时改驱动、材质、场景版本和缓存。

其他勘误：body0/body1确实是relationship；特定MJCF导入失败不能泛化为所有版本永远不支持某标签；导入器外层通常通过引用/变体组合出网格，不能说外层必然看不到网格；UR5e的x≤-1.09只是几何粗估，不是经过姿态、关节限制、碰撞与IK验证的可达域。
